    EMR

    Protocol: JSON 1.1 Endpoint: http://localhost:4566/ Target prefix: X-Amz-Target: ElasticMapReduce.*

    Floci emulates the Amazon EMR (Elastic MapReduce) management API. Clusters (job flows), instance groups and fleets, steps, security configurations, and tags are tracked in Floci's storage backend so the AWS CLI and SDK clients can drive the full cluster lifecycle locally. EMR does not launch real Hadoop/Spark clusters. Clusters transition through their lifecycle states as a state machine. In the docker runner mode Spark steps, commands and scripts run for real, each in a container of its own, after the cluster's bootstrap actions (see Running steps).

    Cluster lifecycle

    In the default immediate runner mode nothing runs, but a cluster and its steps go through the states of the Management Guide's cluster lifecycle, each held for as long as the configuration says. A cluster is STARTING for the first half of cluster-startup-delay-seconds and BOOTSTRAPPING for the second, then RUNNING while it runs steps and WAITING once it has none left. A request's steps are all created PENDING, then start in the order they were added, at most StepConcurrencyLevel at a time, each RUNNING for step-duration-seconds. Steps added while the cluster starts wait for it to be ready. Raising the level with ModifyCluster starts the steps that now fit at once, and lowering it lets the running ones complete. TerminateJobFlows makes a cluster TERMINATING for cluster-termination-delay-seconds and then TERMINATED, and cancels any step not yet completed, as its API reference says. Each call finds the clusters it reads as they stand at that moment. With every duration at its default of 0, a cluster is ready, and its steps complete, before the call that started them returns.

    CancelSteps cancels a PENDING step, and a RUNNING one from release emr-5.28.0, as its API reference says. A cancelled RUNNING step makes room for the next PENDING one. On an earlier release a RUNNING step answers FAILED with "Step is not in a cancellable state: RUNNING".

    A cluster created with Instances.KeepJobFlowAliveWhenNoSteps set to false terminates after its initial steps or steps added later complete, reporting ALL_STEPS_COMPLETED, without waiting first. A cluster with no steps remains WAITING until steps are added. Set KeepJobFlowAliveWhenNoSteps to true to keep the cluster WAITING after its steps complete. Automatic step-completion termination also applies when termination protection is enabled. AddJobFlowSteps rejects a TERMINATING or TERMINATED cluster without adding steps or changing its termination status, and answers an unknown cluster with ValidationException "Specified job flow ID does not exist.", as AWS does. Instance groups and fleets report RUNNING from the cluster's creation until it is TERMINATED. Then they report TERMINATED with zero running or provisioned capacity; their requested and target capacities remain recorded. ListInstances retains each group's instances with their original synthetic IDs and TERMINATED status for 30 days after termination. New groups or fleets are rejected on terminated clusters. As on AWS, ModifyInstanceGroups answers ValidationException "An instance group may only be modified when the cluster is running or waiting." for a cluster in any other state, and ModifyInstanceFleet answers InvalidRequestException "A job flow that is shutting down, terminated, or finished may not be modified." with ErrorCode INVALID_JOB_SHUT_DOWN for a TERMINATING or TERMINATED one, and "An instance fleet may only be modified when the cluster is running or waiting." with ErrorCode MODIFY_INSTANCE_FLEET_OF_RUNNING_JOBFLOW_ONLY for one in any other state, such as STARTING or BOOTSTRAPPING. AddInstanceFleet gives a TERMINATING cluster the "shutting down" answer, and AddInstanceGroups gives it as ValidationException, as AddJobFlowSteps does. InstanceStates filters the modeled RUNNING and TERMINATED instances.

    TerminateJobFlows, the four Set* cluster setters and CancelSteps refuse a request without a member their model requires (JobFlowIds and the setting, or StepIds) with ValidationException "1 validation error detected: Value null at 'jobFlowIds' failed to satisfy constraint: Member must not be null", AWS's framework wording, as RunJobFlow does for Name. They used to read a missing list as empty and a missing setting as its default, and answer success. An empty JobFlowIds is still accepted.

    A state machine drives clusters and steps through the elasticmapreduce: integrations, .sync included; see Step Functions: Amazon EMR tasks.

    Running steps

    With runner-mode set to docker (FLOCI_SERVICES_EMR_RUNNER_MODE=docker), a step runs. Floci starts one container per step from the cluster's release image, the one EMR Serverless's docker mode uses (public.ecr.aws/emr-serverless/spark/<release>), and runs the step in it: a Spark step's spark-submit in local mode, the container holding the driver and its executors, or a command or a script. The cluster itself gets no container, and goes through its lifecycle as in the immediate mode, but for its bootstrap actions and its storage.

    • Which steps run: a command-runner.jar step whose first argument is spark-submit, the way the Management Guide writes Spark steps, runs the arguments after it, without its --master and --deploy-mode. A custom JAR step runs its MainClass, or else the one its manifest names, through spark-submit, with the JAR and the step's Args. Any other command-runner.jar step runs its command, its first argument, with the rest, and a script-runner.jar step (by name, or by its s3://<region>.elasticmapreduce/libs/script-runner/script-runner.jar URI) its script, as the Release Guide's "Run commands and scripts on an Amazon EMR cluster" describes them. An s3-dist-cp step runs Floci's own S3DistCp (see S3DistCp). hive-script, pig-script, hadoop-streaming and hadoop-lzo, which the image does not have, are FAILED without running.
    • Commands and scripts: they run as the image's hadoop user in /home/hadoop, with bash, Python 3, Java, curl and the AWS CLI v2, which reaches Floci through AWS_ENDPOINT_URL. A script-runner.jar step's script is fetched from S3 with the AWS CLI and the step's credentials, then run with the step's other arguments; a path not in S3 is run as it is, a bare name from /home/hadoop when a file there has it, one a former step left there included. hadoop fs and hdfs dfs reach the cluster's HDFS (see Storage). A spark-submit they start runs in local mode on Floci's S3 with the cluster's spark-defaults, core-site, spark-hive-site and spark-log4j2, which Floci puts in a Spark configuration of its own, a copy of the folder a spark-env export of SPARK_CONF_DIR names, else of the image's, ahead of the image's EMR Serverless master; its own --master yarn or --deploy-mode cluster fails, as there is no YARN.
    • Storage: a cluster's primary node keeps its disks while the cluster lives, and so does Floci: each step's container mounts the cluster's two Docker volumes, one at /home/hadoop and one at /mnt, so what a step leaves there is there for the steps after it, and for steps running at the same time. HDFS, "best used for caching the results produced by intermediate job-flow steps", as the Management Guide puts it, is the hdfs folder of /mnt. In Spark, hdfs:// paths, and paths without a scheme ("hdfs:// (or no prefix)"), lead there through Hadoop's ViewFileSystemOverloadScheme, a relative path under /user/hadoop as in HDFS, and a structured streaming query keeps its checkpoints through Spark's file system checkpoint manager; the cluster's spark-defaults and core-site can set any of these otherwise. A command's hadoop fs gets the same, through a copy of the image's Hadoop configuration, or of the folder a spark-env export of HADOOP_CONF_DIR names, with the cluster's core-site after it, which wins; the image's hdfs command cannot run, so hdfs dfs runs as hadoop fs, and its other commands fail. What the bootstrap actions left in /home/hadoop or /mnt comes with the image the steps run in, and Docker copies it into the volumes when the first step starts. The volumes go once the cluster has ended and its last step is done ("HDFS is ephemeral storage that is reclaimed when you terminate a cluster"), on a state reset, and, for clusters that are gone or have ended, when the EMR service starts, unless reconcile-containers-on-startup is off. HDFS is a folder, without a NameNode or replication: an hdfs:// path naming a host is not served, hadoop fs -ls / fails ("URI scheme is not "file""), where -ls -d / and a folder below it do not, and hadoop fs does not reach S3, as its classpath has no AWS SDK v2 and the image's EMRFS is not pointed at Floci (aws s3 cp does). /tmp is each container's own.
    • S3DistCp: the image has neither s3-dist-cp nor MapReduce, so a command-runner.jar step whose first argument is s3-dist-cp, the Release Guide's form, runs Floci's own program instead, through spark-submit in the step's container, copying through Hadoop's file systems: --src and --dest take S3 paths in Floci's S3, the cluster's HDFS (hdfs:///output, or a path without a scheme) or a file of the container, a source folder's files keeping their folders under --dest. It takes the Release Guide's options, --name=value or --name value, and -D property=value. --srcPattern and --groupBy match the whole source path, as Python regular expressions, which share Java's common syntax. --groupBy concatenates the files whose groups give the same name, which is the groups' text, into the folder of the first of them, and refuses a regular expression with no group, as S3DistCp does; --targetSize breaks a group larger than it into parts named with a number before the extension. --outputCodec (gzip, gz, lzo, lzop, snappy, or none to decompress) decompresses each source by its own extension and replaces that extension with the codec's; without it a file's compression stays as it is, and a group keeps the compression its files share, named with that codec's extension, or has none when they differ, each file decompressed so that the group is one stream. --deleteOnSuccess deletes the copied files, but not their folders, once all are copied. --outputManifest writes gzipped JSON lines (path, baseName, srcDir, size) to --dest; --previousManifest leaves out the files it names by baseName, and fails the step when it is not there unless --requirePreviousManifest is false (=false or false after it); --copyFromManifest copies the files it names. --srcPrefixesFile copies the files under each of its lines instead of listing --src, a line ending in / naming that folder alone and any other a prefix as S3 lists one (logs/day takes in logs/day-old/). --s3ServerSideEncryption, --storageClass, --disableMultipartUpload and --multipartUploadChunkSize set S3A's matching settings; --s3Endpoint is ignored, as S3 is Floci's. A bucket name with an underscore fails the step, as S3DistCp "does not support" one, and so does a copy Hadoop fails, leaving what was copied, as S3DistCp does. --appendToLastFile puts the new data after what a destination file holds, through a copy renamed over it, as neither S3 nor the cluster's HDFS, a folder, appends in place. The copy has a name of its own and goes if the writing fails; the file steps aside, under a name of its own too, until the copy has taken its place, and comes back if it cannot, so a failed append leaves it as it was. A copy that would write two files to the same path, the manifest included (a.log and a.log.gz with --outputCodec=gzip, say), a file over one of its own sources, as with the same --src and --dest, a file outside --dest, through a .. in a manifest's baseName or in --outputManifest, or a file with no name, from a --groupBy whose groups matched nothing, say, fails before it writes anything. A step's log has one line saying what was copied. Floci's own readings, as no source says: the grouped file's folder, --numberFiles putting the number straight before the file's name, a group's compression without --outputCodec, and failing a copy that would write over its own output or source, or outside --dest.
    • HTTPS: with TLS on, each step's container, and the bootstrap actions' one, also gets Floci's CA bundle as a Java trust store, which every JVM in it uses, as an EMR Serverless job run's do, so Java code reaches Floci over HTTPS too, and through AWS's own endpoint names with FLOCI_DNS_SPOOF_AWS_ENDPOINTS.
    • Bootstrap actions: a cluster with BootstrapActions is BOOTSTRAPPING until they have run, one after the other, in one container of the release's image, whatever the second half of cluster-startup-delay-seconds. Each action's script is read from Floci's S3 (an s3n:// or s3a:// path names the same bucket, and another path is the image's own) and runs with its Args in /home/hadoop, with the credentials of the cluster's JobFlowRole instance profile, as a step would. "Bootstrap actions execute as the Hadoop user by default", and sudo gives them root, but the image has no sudo: an action runs as root, with a sudo that runs its command as it is, and what it leaves in /home/hadoop is the hadoop user's. Once every action has succeeded, the container is kept as an image named after the cluster, which its steps run in, so that what the actions installed or wrote is there for each of them; the image goes once the cluster has ended and its last step is done. An action that exits with another code than 0 ends the cluster: it cancels its steps and goes TERMINATING, then TERMINATED_WITH_ERRORS, with the reason BOOTSTRAP_FAILURE and AWS's message "On the master instance (i-00000000000000001), bootstrap action 1 returned a non-zero return code", the instance as ListInstances gives the master. A script that cannot be read ends it the same way, in Floci's own words, and a bootstrap that cannot run at all, an image that cannot be pulled say, with INTERNAL_ERROR. TerminateJobFlows stops the actions at once, and a cluster Floci was bootstrapping when it stopped ends with INTERNAL_ERROR once Floci is back. With a LogUri, each action's output goes to stdout.gz and stderr.gz under <LogUri>/<cluster-id>/node/<instance-id>/bootstrap-actions/<n>/, as the Management Guide's bootstrap failure pages give the folder. The actions run once, as on the master: there are no core or task nodes to run them on. Shutdown actions do not run, and Status.ErrorDetails is not given.
    • States: a step is RUNNING from when it starts until its driver or command exits; step-duration-seconds does not apply. The first step of a release also waits while its image is pulled (3.5 to 4.3 GB unpacked; see floci.docker.image-pull-timeout-seconds). It is then COMPLETED on exit code 0, and FAILED otherwise. A FAILED step's Status.FailureDetails has the Reason "Unknown Error", which the API reference says EMR gives when it cannot find the root cause, and a Message in Floci's own words, such as "The Spark driver exited with code 1." or "The step's command exited with code 1.".
    • ActionOnFailure: a failed step's action is taken as the API reference and the Management Guide's termination protection table give it. CONTINUE runs the next step. TERMINATE_CLUSTER (or TERMINATE_JOB_FLOW) ends the cluster, unless it waits after its steps (KeepJobFlowAliveWhenNoSteps) and is termination protected, when it goes on. CANCEL_AND_WAIT cancels the PENDING steps and leaves the cluster WAITING, or ends it when it is set to end after its steps. A cluster a step failure ends cancels its other steps and goes TERMINATING, then TERMINATED_WITH_ERRORS, with the reason STEP_FAILURE and the message "Shut down as step failed". While StepConcurrencyLevel is above 1 no action is taken, and with level 1 and other steps still running CANCEL_AND_WAIT is not either, as the guide says.
    • Cancelling: CancelSteps on a RUNNING step, and TerminateJobFlows, stop its driver at once; a cancelled step takes no ActionOnFailure. A step Floci was running when it stopped is FAILED once Floci is back, and its ActionOnFailure is taken then. Floci's shutdown and a state reset stop every driver, and start no other step; a driver a hard stop left running is removed when the EMR service starts, before any step can start, unless reconcile-containers-on-startup is off.
    • What spark-submit gets: the step's arguments, after the spark-defaults properties of the cluster's Configurations and its core-site and spark-hive-site ones as spark.hadoop. settings, which Spark's Hadoop configuration, and its Hive client's, take as they would core-site.xml and hive-site.xml, so the Management Guide's hive.metastore.client.factory.class for the Glue Data Catalog applies; a spark-hive-site setting wins over the same one in core-site, and a spark.hadoop. setting in spark-defaults over both. s3:// and s3a:// paths reach Floci's S3 through S3A, on releases before 7.10.0 too, where s3:// would otherwise be EMRFS, so the application and its files can be read from there; the Glue Data Catalog client is pointed at Floci's Glue, and hdfs:// paths, and those without a scheme, at the cluster's HDFS. The cluster's spark-log4j2 properties, which "Change values in Spark's log4j2.properties file", follow the log4j2.properties of the folder a spark-env export of SPARK_CONF_DIR names, else of the image's, in a copy of the step's own, a later key winning, so rootLogger.level set to warn quiets Spark's INFO lines. Other classifications (hadoop-env, spark-metrics, spark-log4j for releases before 6.8.0 and the rest) are not applied.
    • A step's Properties: "Java properties that are set when the step runs. You can use these properties to pass key-value pairs to your main function", as the API Reference puts it. A custom JAR step's are system properties of the JVM its main class runs in, which System.getProperty reads, passed to spark-submit in SPARK_SUBMIT_OPTS after any Java options a spark-env export puts there, so a step's own win. A command-runner.jar or script-runner.jar step's would be those of the runner's own JVM, which Floci has none of, and a JVM's system properties do not pass to a process it starts, so they go nowhere. This is Floci's reading, as that sentence is the only source.
    • spark-env: the variables the cluster's spark-env exports, in its nested export classification, are in each step's container environment, PYSPARK_PYTHON or JAVA_HOME say, replacing any of Floci's own with the same name. They are set as given, with no shell expansion of a $VARIABLE in them, and a command or script sees them too, where EMR writes them in spark-env.sh, which only Spark's own scripts read. The image's spark-env.sh gives PYSPARK_PYTHON, PYSPARK_DRIVER_PYTHON, SPARK_HOME and HADOOP_CONF_DIR only a default, so the exports win there, but a variable it sets outright, such as AWS_STS_REGIONAL_ENDPOINTS, keeps the image's value in spark-submit.
    • Credentials: the container gets a session for the step's ExecutionRoleArn, or else for the role of the cluster's JobFlowRole instance profile, when IAM knows it and the profile holds one role, and otherwise the account's placeholder credentials, with AWS_ENDPOINT_URL pointing at Floci.
    • Output: the driver's output goes to Floci's log, prefixed emr:<stepId>. With a LogUri on the cluster, its standard output and error also go to Floci's S3 once the step ends, gzipped, as stdout.gz and stderr.gz under <LogUri>/<cluster-id>/steps/<step-id>/, the step log folder of the Management Guide's "Log locations" (an s3n:// or s3a:// LogUri names the same bucket). A cancelled step's logs hold what its driver wrote until it was stopped. Logs that cannot be written, to a bucket that does not exist say, leave the step as it ended. The controller and syslog logs and the other log folders are not written, nothing is copied while a step runs (EMR copies its logs every five minutes), and FailureDetails has no LogFile.
    • Image: image-template names another image, such as a mirror or a dated tag of the release's image: registry.internal/emr-serverless/spark/%s:20250425. A release with no EMR Serverless image fails its steps with "The step could not start: Could not pull image".

    EventBridge events

    Every state a cluster or a step enters is sent to the default EventBridge bus of its Region, in the account that made the call, as AWS sends it: source aws.emr, detail type EMR Cluster State Change or EMR Step Status Change, an empty resources, and the detail of the EMR Management Guide's examples. A cluster's detail holds severity, stateChangeReason, name, clusterId, state and message; a step's holds severity, actionOnFailure, stepId, name, clusterId, state and message. The severity and message are the ones the guide's "Monitoring Amazon EMR events" tables give each state, with times to the minute (2026-10-24 09:41 UTC).

    Each change sends its events:

    Change Events, in order
    RunJobFlow the cluster STARTING, then each step PENDING
    AddJobFlowSteps each step PENDING
    The cluster is ready, or a step completes the step COMPLETED; each step it makes room for RUNNING; once none is left, the cluster WAITING, or TERMINATED with ALL_STEPS_COMPLETED when it ends after its steps
    A step fails (docker runner mode) the step FAILED; then as its ActionOnFailure goes: as a completed step, or CANCELLED for each step it cancels and the cluster WAITING, or CANCELLED for each step not yet completed and the cluster TERMINATED_WITH_ERRORS with STEP_FAILURE
    TerminateJobFlows CANCELLED for each step not yet completed; the cluster TERMINATED with USER_REQUEST once it has been TERMINATING for the delay, also when a protected cluster fails the call
    CancelSteps CANCELLED for each step it cancels, and RUNNING for the step a cancelled RUNNING one makes room for

    A change that falls due between calls, such as a step completing after step-duration-seconds, is made at that time and its events sent then, whether or not anything reads the cluster.

    A STARTING or WAITING cluster's stateChangeReason is {"code":""}, as in the guide's example, and a terminated one's carries the reason's code and message, such as {"code":"USER_REQUEST","message":"Terminated by user request"}. TERMINATED is INFO for USER_REQUEST and ALL_STEPS_COMPLETED and CRITICAL for any other reason, and TERMINATED_WITH_ERRORS is CRITICAL; a cancelled step is WARN and a failed one ERROR. The tables have no row for a cluster's BOOTSTRAPPING, RUNNING or TERMINATING, which send nothing, so a WAITING cluster that runs added steps sends WAITING again when they are done. The guide gives two WAITING messages without saying when each applies: a cluster that ran steps reports it "finished running all pending steps", one that did not that it "was created ... and is ready for use".

    Events go out in the order their changes were made, once the call that made them no longer holds the cluster. A rule's target that calls EMR while an event is delivered, such as one ending the cluster on its STARTING event, has its events sent after the rest of that call's.

    Configuration

    Variable Default Description
    FLOCI_SERVICES_EMR_ENABLED true Enable or disable the service
    FLOCI_SERVICES_EMR_DEFAULT_RELEASE_LABEL emr-7.5.0 The release label of a cluster created without one; see Release catalogue
    FLOCI_SERVICES_EMR_CLUSTER_STARTUP_DELAY_SECONDS 0 Seconds a new cluster takes to be ready to run steps, the first half STARTING and the second BOOTSTRAPPING; 0 makes it ready as soon as it is created
    FLOCI_SERVICES_EMR_STEP_DURATION_SECONDS 0 Seconds a step stays RUNNING before it completes; 0 completes it as soon as it starts
    FLOCI_SERVICES_EMR_CLUSTER_TERMINATION_DELAY_SECONDS 0 Seconds a cluster stays TERMINATING before it is TERMINATED; 0 ends it at once
    FLOCI_SERVICES_EMR_RUNNER_MODE immediate immediate completes steps by time without running anything; docker runs each step in a container, after the cluster's bootstrap actions (see Running steps)
    FLOCI_SERVICES_EMR_DOCKER_NETWORK the global default Docker network for step containers
    FLOCI_SERVICES_EMR_IMAGE_TEMPLATE public.ecr.aws/emr-serverless/spark/%s:latest, or spark4/ in place of spark/ for an emr-spark-* release Image for a docker step, %s standing for the cluster's release label
    FLOCI_SERVICES_EMR_RECONCILE_CONTAINERS_ON_STARTUP true Remove the step drivers and bootstrap containers a previous run of this Floci left on the Docker daemon, and the images bootstrap actions left for clusters that are gone or have ended, when the EMR service starts; turn it off when two Floci instances share a daemon with the same port and no resource namespace

    Release catalogue

    ListReleaseLabels, DescribeReleaseLabel and ListSupportedInstanceTypes read a curated catalogue, not AWS's full list: emr-7.5.0 (Floci's default), emr-7.4.0, emr-6.15.0, emr-6.14.0 and emr-5.36.2. Each release's applications and versions come from its page in the Amazon EMR Release Guide, with names lowercased and AWS's -amzn-N build suffix dropped, as the API reports them, and its two most recent Amazon Linux releases. A floci.services.emr.default-release-label outside the catalogue is still listed, with no applications.

    ListReleaseLabels filters by Prefix (such as emr-6) and Application (spark or spark@3.4.1, matched without regard to case) and pages with MaxResults (1 to 100) / NextToken; a token only works with the filters it was issued for. DescribeReleaseLabel answers every application at once, since AWS reserves its MaxResults and NextToken for future use. ListSupportedInstanceTypes reports common families (c5, m5, m5d, m6g, r5, r6g) with their EC2 sizes. An unknown release label, a bad token or an out-of-range MaxResults is InvalidRequestException. RunJobFlow does not check its release label or instance types against the catalogue.

    Example

    export AWS_ENDPOINT_URL=http://localhost:4566

# Create a cluster
CLUSTER_ID=$(aws emr run-job-flow \
  --name "demo-cluster" \
  --release-label emr-7.0.0 \
  --instances KeepJobFlowAliveWhenNoSteps=true,InstanceGroups='[{InstanceCount=1,InstanceGroupType=MASTER,InstanceType=m5.xlarge}]' \
  --query 'JobFlowId' --output text)

# Inspect it
aws emr describe-cluster --cluster-id "$CLUSTER_ID"
aws emr list-clusters

# Add a step
aws emr add-steps --cluster-id "$CLUSTER_ID" \
  --steps Type=CUSTOM_JAR,Name=demo,Jar=command-runner.jar,Args=[echo,hello]

# Terminate
aws emr terminate-clusters --cluster-ids "$CLUSTER_ID"

    aws emr add-steps --execution-role-arn applies the role to every step in that request. RunJobFlow also applies StepExecutionRoleArn to its initial steps. describe-step includes ExecutionRoleArn for those steps; list-steps returns step summaries without it.
