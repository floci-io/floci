    EMR Serverless

    EMR Serverless is an AWS service that provides serverless data analytics environments. Floci provides an emulator for the management-plane API (REST JSON) which covers the lifecycle of an Application, of the job runs submitted to it and of its Spark Connect sessions.

    Configuration

    Key Description Default
    floci.emrserverless.enabled Whether the EMR Serverless API is enabled true
    floci.emrserverless.port The port the service is exposed on 4566
    floci.services.emrserverless.job-run-duration-seconds How long a BATCH job run stays RUNNING before it succeeds; 0 makes it SUCCESS as soon as it starts 0
    floci.services.emrserverless.runner-mode immediate moves job runs and sessions through their states without running anything; docker runs each job run, and each session's Spark Connect server, in a container (see Running Spark job runs, Running Hive job runs and Running a session's Spark Connect server) immediate
    floci.services.emrserverless.docker-network Docker network for job run containers the global default
    floci.services.emrserverless.image-template Image for a docker job run whose application names no custom image, %s standing for the release label public.ecr.aws/emr-serverless/spark/%s:latest, or spark4/ in place of spark/ for an emr-spark-* release
    floci.services.emrserverless.hive-image-template Image for a docker Hive job run whose application names no custom image, %s standing for the release label public.ecr.aws/emr-serverless/hive/%s:latest
    floci.services.emrserverless.executor-containers How many executors a docker Spark job run may have at once, each in a container of its own (see Executors under Running Spark job runs); 0, the default, runs a run's executors in its driver's container, in Spark's local mode 0
    floci.services.emrserverless.honour-architectures Run a docker job run's driver and executors for its application's architecture (see Architecture under Running Spark job runs); false runs them on the Docker host's own platform false
    floci.services.emrserverless.reconcile-containers-on-startup Remove the drivers and executors a previous run of this Floci left on the Docker daemon before the first job run starts; turn it off when two Floci instances share a daemon with the same port and no resource namespace true

    Endpoints

    The emulator implements the standard AWS emr-serverless service endpoints:

    • POST /applications (CreateApplication)
    • GET /applications (ListApplications)
    • GET /applications/{applicationId} (GetApplication)
    • PATCH /applications/{applicationId} (UpdateApplication)
    • DELETE /applications/{applicationId} (DeleteApplication)
    • POST /applications/{applicationId}/start (StartApplication)
    • POST /applications/{applicationId}/stop (StopApplication)
    • POST /applications/{applicationId}/jobruns (StartJobRun)
    • GET /applications/{applicationId}/jobruns (ListJobRuns)
    • GET /applications/{applicationId}/jobruns/{jobRunId} (GetJobRun)
    • DELETE /applications/{applicationId}/jobruns/{jobRunId} (CancelJobRun)
    • GET /applications/{applicationId}/jobruns/{jobRunId}/attempts (ListJobRunAttempts)
    • GET /applications/{applicationId}/jobruns/{jobRunId}/dashboard (GetDashboardForJobRun)
    • POST /applications/{applicationId}/sessions (StartSession)
    • GET /applications/{applicationId}/sessions (ListSessions)
    • GET /applications/{applicationId}/sessions/{sessionId} (GetSession)
    • DELETE /applications/{applicationId}/sessions/{sessionId} (TerminateSession)
    • GET /applications/{applicationId}/sessions/{sessionId}/endpoint (GetSessionEndpoint)
    • GET /applications/{applicationId}/dashboard (GetResourceDashboard)
    • POST /tags/{resourceArn} (TagResource)
    • DELETE /tags/{resourceArn}?tagKeys=... (UntagResource)
    • GET /tags/{resourceArn} (ListTagsForResource)

    The tagging operations work on application, job run and session ARNs, as CreateApplication, StartJobRun and StartSession return them (arn:aws:emr-serverless:<region>:<account>:/applications/<id>, .../applications/<id>/jobruns/<id> and .../applications/<id>/sessions/<id>). They share the tags those calls store, so GetApplication, GetJobRun and GetSession always report the current set. Following the EMR Serverless user guide, a resource holds at most 50 tags, and aws: in any case is reserved as the prefix of a tag key or value. Once an application is deleted, its ARN and its runs' and sessions' ARNs answer ResourceNotFoundException too, while GetApplication, GetJobRun and GetSession still report them.

    Applications, job runs, sessions, creation client tokens, and tags are scoped to the request's AWS Region. An application, run or session created in one Region is not returned by list, get, or tag requests signed for another.

    ListApplications refuses a states filter naming a state that does not exist, or more than 7, and a maxResults outside 1 to 50, with the ValidationException AWS's validation layer answers.

    CreateApplication stores every configuration UpdateApplication does, runtimeConfiguration, monitoringConfiguration, schedulerConfiguration, diskEncryptionConfiguration, interactiveConfiguration, identityCenterConfiguration and jobLevelCostAllocationConfiguration among them, and GetApplication returns each as it was written, except for schedulerConfiguration (see Concurrency and queuing under job runs).

    UpdateApplication answers with the updated application, as GetApplication reports it.

    UpdateApplication changes any setting of a CREATED or STOPPED application, and of a STARTED one its maximumCapacity and its custom images, imageConfiguration and workerTypeSpecifications, as the user guide's "Updating Running Applications" describes, and a schedulerConfiguration naming only maxConcurrentRuns, as its "Job concurrency and queuing" page has it. For every other setting the API reference's "An application has to be in a stopped or created state in order to be updated" holds: a STARTED application's update naming one, even beside those or with its current value, is refused with ValidationException, "Application must be in a stopped or created state in order to be updated.", and so is an image change on an application with initialCapacity ("Custom image updates on running applications are not supported on applications with pre-initialized capacity configured"). A run already going keeps the image and the maximum capacity it was launched with, and a new run, or a new attempt of a run, takes the application's current ones: "New workloads submitted after the update automatically will use the new image, while existing workloads continue with the original image". On a release up to 7.13 whose applicationLevelDigestResolution is left true, or any whose image configuration sets it true, "Custom images are resolved to a digest at application start; that digest is used for all jobs until the application restarts": a new run keeps the image the application resolved as it started (see Image under job runs) until it starts again, unless the update turns that image configuration's applicationLevelDigestResolution to false, after which each run resolves the image it is given.

    DeleteApplication leaves the application in TERMINATED state. GetApplication continues to report that state so lifecycle waiters can observe it, while an unfiltered ListApplications omits the terminated application. A terminated application cannot be started or stopped again.

    Job runs

    In the default immediate runner mode, job runs are metadata only: nothing executes. A run follows the job run states and GetJobRun's response shape, and settles when it is read. In the docker runner mode a Spark run executes; see Running Spark job runs.

    • Lifecycle: a run is RUNNING from the moment it is submitted, or from the moment it leaves the queue (see Concurrency and queuing). With the default job-run-duration-seconds of 0, a BATCH run is SUCCESS as soon as it starts; a positive duration keeps it RUNNING that long. A run whose duration would pass its executionTimeoutMinutes (720 when not given, as AWS reports it) is CANCELLED at the timeout. A STREAMING run stays RUNNING until it is cancelled.
    • Concurrency and queuing: as the user guide's "Job concurrency and queuing for an EMR Serverless application" describes, at most maxConcurrentRuns of an application's batch and streaming runs run at once. A run submitted beyond that is QUEUED, and the first queued run starts when one of them ends or is cancelled. A run still queued queueTimeoutMinutes after it was submitted is CANCELLED, as the job run states give a run that "has timed out" as a reason to be cancelled. Its stateDetails is Floci's wording, as no source gives AWS's. A run that leaves the queue reports queuedDurationMilliseconds. A queued run is cancelled at once, and keeps StopApplication from stopping the application. Queuing is "supported on Amazon EMR release 7.0.0 and higher" and "enabled by default on Amazon EMR release 7.3.0 and higher", the AWS runtime for Apache Spark's releases included. An application that sets no schedulerConfiguration queues only from 7.3.0, with the defaults of 15 runs and 360 minutes. maxConcurrentRuns must be 1 to 1000 and queueTimeoutMinutes 15 to 720, or the request is refused with ValidationException, in Floci's wording. Terraform's acceptance tests record how AWS keeps the configuration. A member a request leaves out takes its default, and here keeps the value already set where there is one. An empty object turns queuing off, on 7.3.0 and later too, and the application then returns no schedulerConfiguration. Raising maxConcurrentRuns on a STARTED application starts queued runs at once. With the default job-run-duration-seconds of 0, a BATCH run ends as it starts and never holds a slot, so only STREAMING runs, or runs given a duration, wait.
    • Auto-start: a run submitted to a CREATED or STOPPED application starts the application, as autoStartConfiguration.enabled defaults to true. With auto-start turned off, the run is refused with ValidationException until the application is started. A run on a terminated application is refused.
    • Idempotency: clientToken is the idempotency token. Repeating a request with the same token returns the original run; reusing the token with a different request answers ConflictException (HTTP 409) "Request did not match the original". The two are compared as the run each would start holds them: executionTimeoutMinutes left out or 720, and tags left out or empty, count as the same; a member the run would hold otherwise, such as a mode given where the original left it out, or a tag with an empty value, does not.
    • Execution timeout: executionTimeoutMinutes is 0 to 1,000,000, 0 meaning no timeout. From release emr-7.11.0, a BATCH run's timeout must be 1 to 10080 minutes (7 days), as the model and the 7.11.0 release notes say; a run outside that is refused with ValidationException. The AWS runtime for Apache Spark's releases, emr-spark-8.0.0 on, hold their BATCH runs to it too: the notes apply it "from this release onwards", and the release list puts them after EMR Serverless 7.14.0.
    • CancelJobRun moves a run that has not finished to CANCELLED. A finished run answers ValidationException "Job run is not in a cancellable state". In the docker mode, from release emr-7.9.0 on, a RUNNING run gets the shutdownGracePeriodInSeconds it is cancelled with, "during which the job can perform cleanup operations prior to final termination": its driver gets SIGTERM, which runs its JVM shutdown hooks, the run is CANCELLING until the driver ends, and a driver still running when the period ends is stopped. "The default behavior for shutdown is to have no grace period" for a BATCH run, and a STREAMING run has a "120-second grace period enabled by default"; 0 is "Immediate termination". "Grace period shutdown is only available for jobs in RUNNING state", so a run that has not started yet, or one on an earlier release, is stopped at once, and "Subsequent cancel requests during the CANCELLING state are ignored". A value other than 0 or 15 to 1800, the user guide's "Valid Range for Shutdown Grace period", is refused with ValidationException, in Floci's own wording.
    • StartJobRun keeps the run's flexExecution ("The Amazon EMR Serverless Flex settings for the job run"), which GetJobRun, ListJobRuns and ListJobRunAttempts give back; an enabled that is not a boolean is refused with SerializationException. Floci has no Flex capacity to run it on, so it changes nothing else.
    • Resource utilization: an ended Spark run gives its totalResourceUtilization, "The aggregate vCPU, memory, and storage resources used from the time the job starts to execute, until the time the job terminates, rounded up to the nearest second", and its billedResourceUtilization, which includes "a 1-minute minimum usage for workers, plus additional storage over 20 GB per worker". Floci reckons both from the workers the run asks for, its driver and the executors it starts with, sized as the user guide's "Supported worker configurations" size them: a worker has the vCPUs its cores ask for, and memory for its Spark memory and that memory's overhead, "10% of container memory, with a minimum of 384 MB", rounded up to the sizes its vCPUs allow. Unset, a worker has 4 vCPUs, 14G of Spark memory and 20G of disk, and a run starts 3 executors, as the "Spark job properties" give them, so a default worker is 4 vCPUs, 16 GB and 20 GB; spark-submit's --driver-cores, --driver-memory, --executor-cores, --executor-memory and --num-executors set over what --conf sets, as Spark takes them. Its driver's worker counts for the whole attempt. Where its executors have containers of their own (see Executors), each executor's worker counts for the time its container ran, as they come and go with Spark's target; otherwise the executors it starts with count for the whole attempt. Each attempt gives its own, and one that never started used nothing. A Hive run gives none, its Tez tasks coming and going with its query.
    • StopApplication refuses an application with a run that has not finished, a STREAMING run or a CANCELLING one included, as the API reference says "All scheduled and running jobs must be completed or cancelled before stopping an application." It answers ValidationException, the one error the model declares for this, with that sentence as its message: AWS's own message is not recorded, so the wording is Floci's reading. It terminates the application's sessions (see Sessions).
    • ListJobRuns returns the newest runs first, the later of two started within the same millisecond first too, filtered by states, createdAtAfter, createdAtBefore and mode, at most 50 per page. With several states, the runs are grouped by state in the order the filter names them. A state or mode that does not exist, or more than 8 states, is refused with ValidationException. An unknown application has no runs. A nextToken resumes only the listing it came from, with the same application and filters.
    • Attempts: a run starts as attempt 1, and in the immediate mode, where none fails, it stays its only one. In the docker mode a run whose driver fails is tried again on release 7.1.0 or later, as the user guide's "Job resiliency" gives it: a BATCH run until it has made retryPolicy.maxAttempts attempts (1 by default, no retry), and a STREAMING run until it has failed maxFailedAttemptsPerHour times within an hour (5 by default). Either outside 1 to 10, the user guide's "Accepted values", is refused with ValidationException, and either not an integer with SerializationException. Each new attempt is SCHEDULED again and runs its driver from the beginning; a cancelled run, one past its timeout, and one Floci's own shutdown stopped are not tried again. GetJobRun without attempt returns the latest attempt, with attempt an earlier one as it ended (FAILED, with its stateDetails), and an attempt the run never made answers ResourceNotFoundException; one below 1 or not an integer is ValidationException. ListJobRunAttempts lists every attempt, oldest first, each with its own creation and update times. No source says whether a run's timeout spans its attempts; Floci applies it to each.
    • createdBy is the caller's ARN, as GetCallerIdentity reports it. releaseLabel and networkConfiguration come from the application.
    • Dashboard: GetDashboardForJobRun gives "a URL that you can use to access the application UIs for a job run", for the latest attempt or the attempt asked for, checked as GetJobRun checks it, and, as AWS's, "The URL is valid for one hour after you generate it". "For jobs in a running state, the application UI is a live user interface such as the Spark or Tez web UI. For completed jobs, the application UI is a persistent application user interface such as the Spark History Server or persistent Tez UI." With runner-mode set to docker, a Spark run's link opens both for real, through Floci, each on a host of its own, http://<secret>-<port>.emr-serverless-ui.<Floci's host and port>/, the secret 26 random letters and digits that only this link holds, so the host itself is the link's authority, as the UI takes no AWS credentials. Floci's host must resolve its subdomains: localhost and localhost.floci.io do, and Floci's TLS certificate names *.emr-serverless-ui.localhost and *.emr-serverless-ui.localhost.floci.io. A link's host answers with a 403 page once its hour has passed, or when it was given before Floci restarted.
    • While the attempt runs, the link, on port 4040, opens its driver's Spark UI: port 4040 of its container, which Docker publishes on the host's loopback interface alone, or which Floci, in a container on the same network, reaches there. The release's image turns the UI off; Floci turns it on before the run's own settings, so a run that turns it off again has none. Until the driver runs, and then until its Spark has started the UI, or for good where the run turned it off, the host answers with a 503 page asking to try again, and once the attempt has ended, with a 404 one.
    • Once the attempt has ended, the link, on port 18080, opens a Spark History Server over the run's event logs, for the 30 days EMR Serverless keeps them: "By default, EMR Serverless stores application logs securely in Amazon EMR managed storage for a maximum of 30 days". The run's driver writes its event logs where the release's image says (spark.eventLog.dir, file:///var/log/spark/apps), on a Docker volume of the run's own, every attempt's there, and the server runs in a container of the release's image that starts as its link is first opened, the host answering with a 503 page until it answers, and stops once no link to it is valid. The server lists the run's applications, one per attempt, rather than opening the attempt's. A history goes 30 days after its run ended, or once its run has gone, which Floci checks as it starts and every hour; a restart keeps the histories, and a reset removes them all. Each history and its server carry the owner label of the Floci that keeps them, so another Floci sharing the Docker daemon leaves them alone. Where Docker cannot tell whether a history is kept, its host answers with the 503 page too, rather than taking the history for gone.
    • Otherwise, the link opens a page Floci serves at /_aws/emr-serverless/dashboard on its own address (base-url, or hostname): for a run whose logs are not kept in managed storage, its managedPersistenceMonitoringConfiguration, or else its application's, with enabled false, as with logs in S3 alone the application UI is "Not supported" ("Otherwise, you can't use the built-in application UIs"), so Floci keeps none of its event logs; for a run that turns its event logs off (spark.eventLog.enabled) or sends them elsewhere (spark.eventLog.dir), as nothing is kept for a history server to read; for a Hive run, as Floci runs no Tez UI; once a history has gone; and in the immediate mode. The page shows the attempt's state, its times, where its driver's logs go in S3 and in CloudWatch Logs, and whether they are kept in managed storage, kept as the attempt was admitted, so a later change to the application's monitoring configuration does not move them. Its link names the run and is signed with a key Floci makes as it starts: one changed, or past its hour, or given before Floci restarted, opens a 403 page asking for a new one, and one whose run has gone a 404.

    Like the rest of Floci, no link asks for credentials. AWS's link, by a user's report, opens a limited number of times ("This URL has already been used the maximum number of times. Please generate a new URL."); Floci's open as often as asked within their hour. accessSystemProfileLogs, for jobs on Lake Formation, changes nothing.

    Sessions

    A session is "a managed connection between your local PySpark client and a Spark driver running on Amazon EMR Serverless", through Spark Connect. With runner-mode set to docker, Floci runs that driver, a Spark Connect server, in a container, and a client reaches it through Floci (see Running a session's Spark Connect server). With the default immediate mode, Floci keeps a session and its lifecycle but runs no driver for it.

    • Starting: StartSession needs a Spark application on emr-7.13.0 or later, or on the AWS runtime for Apache Spark (emr-spark-8.0.0 on), whose interactiveConfiguration.sessionEnabled is true. As for a job run, a CREATED or STOPPED application is started unless its auto-start is off, when the session is refused, and so is one on a terminated application. Each of these refusals is ValidationException in Floci's own wording, as AWS's is not recorded. clientToken is the idempotency token, compared as for a job run: idleTimeoutMinutes left out or 60, tags left out or empty, and configurationOverrides without a runtimeConfiguration count as the same. An application holds at most 25 sessions that have not ended, as "Each EMR Serverless application supports up to 25 concurrent sessions by default"; a 26th is refused with ServiceQuotaExceededException (HTTP 402). Of configurationOverrides, only runtimeConfiguration is kept: "Only runtime configuration overrides are supported." A runtimeConfiguration with a member of the wrong JSON type is refused with SerializationException, and a configuration without its classification with ValidationException. releaseLabel and networkConfiguration come from the application, and createdBy is the caller's ARN.
    • States: in the immediate mode a session is IDLE as soon as it starts, with startedAt and idleSince set; in the docker mode it goes through SUBMITTED, STARTING and IDLE, then BUSY and back (see below). It is TERMINATED once it has been idle for its idleTimeoutMinutes (0 to 1,000,000, 60 when not given, as "Default timeout is set to 1 hour"), or once 24 hours have passed since it started, as "Each session has a hard limit of 24 hours by default", whichever comes first. No source says what an idle timeout of 0 does; Floci reads it as no idle timeout, as for a job run's executionTimeoutMinutes. Floci never reports STARTED.
    • TerminateSession ends a session with no server at once as TERMINATED; one whose server runs is TERMINATING until its container has stopped, as "After you terminate a session, it enters the TERMINATING state and then the TERMINATED state". A session that has already ended is refused with ValidationException, in Floci's own wording.
    • StopApplication terminates the application's sessions that have not ended, with stateDetails saying so. The API reference requires a stopping application's job runs to have ended but names no such requirement for sessions, and once an application is stopped "no resources are running on the application"; AWS's own handling is not recorded.
    • GetSessionEndpoint answers for a session that has not ended with Floci's own address as its endpoint, such as http://localhost:4566, and a fresh authentication token that expires in an hour, as "Authentication tokens are time-limited to 1 hour". AWS's endpoint is an https:// URL without a port; a Spark Connect URL holds no path, so Floci's is its address alone, port included, and the token names the session. A session that has ended, or is TERMINATING, is refused with ValidationException, in Floci's own wording.
    • ListSessions returns the newest sessions first, as ListJobRuns orders runs, filtered by states, createdAtAfter and createdAtBefore, at most 50 per page, grouped by state as ListJobRuns groups runs.
    • GetResourceDashboard takes a resourceType of SESSION, the only one, and gives a link like GetDashboardForJobRun's, valid for an hour: "While a session is active, the URL opens the live Apache Spark UI", and "After a session ends, the Spark History Server remains available". With runner-mode set to docker, a link given before the session has ended, or begun to, opens its Spark Connect server's Spark UI, and one given after, for 30 days, a Spark History Server over its kept event logs, as a run's link opens its driver's (see Running a session's Spark Connect server); any other, one given while the session is TERMINATING among them, opens a page about the session on Floci's address. accessSystemProfileLogs changes nothing.

    A state machine drives applications and job runs through the emr-serverless: integrations, .sync included; see Step Functions: Amazon EMR Serverless tasks.

    Running a session's Spark Connect server

    With runner-mode set to docker, each session runs a Spark Connect server in a container, as a job run's driver runs: in the release's image, or the application's custom image, on the same Docker network, with the execution role's credentials, and with its executors in containers of their own when executor-containers is above 0. Its spark-defaults are the application's runtime configuration, then the session's runtimeConfiguration, merged as a job run's applicationConfiguration is. Floci sets spark.connect.grpc.binding.port itself and drops a spark.connect.grpc.binding.address, as that setting "is reserved by EMR Serverless and cannot be overridden by users". The server's port is published on the Docker host's loopback interface only, and clients reach it through Floci.

    • Connecting: build the connection string from GetSessionEndpoint's answer as AWS's guide does, with the token in the x-aws-proxy-auth parameter, but keep the endpoint's port:
    endpoint = emr.get_session_endpoint(applicationId=app_id, sessionId=session_id)
scheme, address = endpoint["endpoint"].split("://", 1)  # http, localhost:4566
tls = ";use_ssl=true" if scheme == "https" else ""
spark = SparkSession.builder.remote(
    f"sc://{address}/{tls};x-aws-proxy-auth={endpoint['authToken']}").getOrCreate()

    Floci serves plain HTTP unless its TLS is on, so use_ssl=true goes only with an https:// endpoint, and then the client has to trust Floci's CA (GRPC_DEFAULT_SSL_ROOTS_FILE_PATH for PySpark). The endpoint is floci.base-url, as every URL Floci hands out is, so where Floci is reached through another port, as a container's mapped port, set floci.base-url to that address. As AWS says, the client's PySpark must match the release's Spark (3.5.6 for emr-7.13.0). * Tokens: a call whose token Floci did not give, or which has expired, fails with gRPC's UNAUTHENTICATED, as "When a token expires, gRPC calls fail with an authentication error". A call to a session that is not IDLE or BUSY, or, in the immediate mode, to any session, fails with UNAVAILABLE, in Floci's own wording. * States: a session is SUBMITTED until its container runs, STARTING until the server answers, then IDLE, with startedAt and idleSince set. No source says when a session is BUSY: Floci makes it BUSY while a call runs on its server, and IDLE again once none does, its idle timeout counting from then. A server that does not answer within 10 minutes, or stops on its own, fails its session with stateDetails saying so (why it did not answer, or its exit code); one Floci stopped running when it restarted fails too, and its container, if one is left, goes. The 24 hours count from when the server answers. * Logs: no source gives where a session's driver logs go, so Floci sends the server's output to its own log only, not to the application's monitoring configuration. * Spark UI: GetResourceDashboard's link opens the server's Spark UI on a host of its own, as a run's link opens its driver's (see Dashboard under job runs): port 4040 of the server's container, published on the host's loopback interface alone. Its host answers with a 503 page until the server's container runs, and with a 404 one once the session has ended. The server keeps its event logs on a volume of the session's own, so once the session has ended a new link opens a Spark History Server over them, for 30 days, as a run's does.

    Running Spark job runs

    With runner-mode set to docker (FLOCI_SERVICES_EMRSERVERLESS_RUNNER_MODE=docker), a Spark job run executes. Floci starts one container per run from the application's custom image, if it names one (see Image below), or else from the release's image, the base image AWS publishes for customizing EMR Serverless images (public.ecr.aws/emr-serverless/spark/<release>, and spark4/<release> for the AWS runtime for Apache Spark releases, emr-spark-8.0.0 on), and runs spark-submit in it, in Spark's local mode by default: the container holds the driver and its executors. With executor-containers above 0, each executor runs in a container of its own instead, as each has a worker of its own on EMR Serverless (see Executors below).

    • Executors: with executor-containers above 0, Floci starts an executor's container as the driver asks for one, of the same image as the driver's or the application's for its executors (see Image), on the same network, with the same credentials and trust store. Its worker offers the run's spark.executor.cores and spark.executor.memory, which Floci reads from the running driver, so they come from the image's spark-defaults, the run's configuration or its sparkSubmitParameters alike: 4 cores and 14 GB unless the run says otherwise. How many run follows Spark's dynamic allocation, on by default, which starts with spark.dynamicAllocation.initialExecutors (3) and releases an idle executor after spark.dynamicAllocation.executorIdleTimeout, when its shuffle data allows: Floci removes the container of an executor Spark released. With dynamic allocation off, spark.executor.instances start. A run has at most executor-containers executors at once, and none that would take the workers of its application's runs, their drivers' among them, past the application's maximumCapacity, which "is cumulative across all workers at any given point in time" and of which "no new resources will be created once any one of the defined limits is hit": a worker counts its cores, its memory with Spark's overhead rounded up to a whole GB, and its disk, spark.emr-serverless.executor.disk or spark.emr-serverless.driver.disk, 20 GB by default. The overhead is the run's spark.executor.memoryOverhead (or the driver's), else that share of the memory its spark.executor.memoryOverheadFactor gives, else spark.emr-serverless.memoryOverheadFactor's, else 10%, and at least 384 MB. The master's address, the run's secret and the UI's kill links (see below) come after the run's own options, so none of them replaces these. Every executor's container goes with its driver, however the run ends, as does one that ended before it, and a hard stop's leftovers go as its driver's do. With executor-containers at 0, the default, or on the host's network or another container's network namespace, where two runs' ports would meet, the executors run in the driver's container instead, in Spark's local mode.

    • States: a run beyond its application's maxConcurrentRuns is QUEUED first, its container not started until it leaves the queue (see Concurrency and queuing under job runs). A run is SCHEDULED while its image is pulled and its container starts (the first run of a release pulls its image, 3.5 to 4.3 GB unpacked; a pull still downloading after floci.docker.image-pull-timeout-seconds, five minutes by default, is tried again, three attempts in all, so on a slow connection raise it or run docker pull on the image first, or the run is FAILED with "Could not pull image"), and RUNNING once the Spark driver runs, which sets startedAt. It is SUCCESS when the driver exits with code 0 and FAILED otherwise, with the exit code in stateDetails. CancelJobRun, or a BATCH run passing its executionTimeoutMinutes, makes it CANCELLING until the driver is stopped, or ends within its grace period (see CancelJobRun above), then CANCELLED, as the job run states describe. A run Floci was running when it stopped is FAILED once it is read again. Floci's shutdown and a state reset stop every driver, one whose image is still being pulled included, and a driver a hard stop left running is removed the first time job runs are used after Floci restarts, unless reconcile-containers-on-startup is off.

    • What spark-submit gets: the entryPoint, its entryPointArguments and the sparkSubmitParameters, after the spark-defaults properties of the application's runtimeConfiguration, or the run's own in configurationOverrides.applicationConfiguration, which replace the application's whole spark-defaults classification. From emr-spark-8.1.0 the two are merged by property instead, the run's winning. s3:// and s3a:// paths reach Floci's S3 through S3A, on releases before 7.10.0 too, where s3:// would otherwise be EMRFS; the entry point and its files can be read from there. The Glue Data Catalog client is pointed at Floci's Glue, with the run's account as its hive.metastore.glue.catalogid (from emr-7.10.0 the client would otherwise ask STS for it), which a spark.hadoop.hive.metastore.glue.catalogid in the spark-defaults replaces.
    • Driver environment and archives: a spark.emr-serverless.driverEnv.<KEY> property, from the spark-defaults above or a --conf in sparkSubmitParameters, which wins, is an environment variable of the container, replacing one of Floci's own of that name, such as the user guide's JAVA_HOME for Java 17. Each archive of spark.archives (which spark-submit's --archives sets, winning over a --conf) that is in Floci's S3 is unpacked into the container's working directory, /home/hadoop in the release's image, before the driver starts, under the name that follows its #, or else its file's name: a .jar or .zip is unzipped, a .tar.gz, .tgz or .tar untarred, and any other file copied, as Spark unpacks one. So the user guide's Python virtual environment runs as it is written there:
    --conf spark.archives=s3://amzn-s3-demo-bucket/EXAMPLE-PREFIX/pyspark_venv.tar.gz#environment
--conf spark.emr-serverless.driverEnv.PYSPARK_DRIVER_PYTHON=./environment/bin/python
--conf spark.emr-serverless.driverEnv.PYSPARK_PYTHON=./environment/bin/python
--conf spark.executorEnv.PYSPARK_PYTHON=./environment/bin/python

    Floci reads each archive as the run's account. One it cannot read fails the run before its driver starts, with "Job run could not start" naming it, and one that does not unpack fails the run as a driver's failure does. Spark also unpacks every archive itself, into its own files folder, where SparkFiles.get finds it, and, with executors in containers of their own, into each executor's working directory. A spark.executorEnv.<KEY> needs nothing more from Floci: Spark gives these variables to its executors, in the driver's JVM in local mode, and the Python workers they start. * Credentials: the container gets a session for the run's execution role when IAM knows the role, otherwise the account's placeholder credentials, and AWS_ENDPOINT_URL pointing at Floci, so the job's own SDK clients reach Floci too. A run's executionIamPolicy.policy scopes that session as an assumed role's session policy does, so with IAM enforcement on "The resulting job IAM role permissions will be an intersection of this policy and the policy associated with your job execution role". Its policyArns are kept and given back but not applied, as Floci's IAM applies no managed session policy, an assumed role's included. StartJobRun refuses an inline policy outside 1 to 2,048 characters, more than 10 policy ARNs, or one outside 20 to 2,048 characters, with the framework's ValidationException, and either member of another JSON type with SerializationException. Only those two members are kept. * HTTPS: with TLS on, the container also gets Floci's CA bundle as a Java trust store, /etc/floci-ca-bundle.p12, which every JVM in it uses through JAVA_TOOL_OPTIONS, each saying so on its standard error (Picked up JAVA_TOOL_OPTIONS: ...); a trust store the job names itself, with -Djavax.net.ssl.trustStore, replaces it. So the job trusts Floci over HTTPS, and with FLOCI_DNS_SPOOF_AWS_ENDPOINTS on as well, which leads AWS's own endpoint names to Floci, SDK clients that ignore AWS_ENDPOINT_URL, the AWS SDK for Java 1.x's for one, reach Floci unchanged. * Output: the driver's output goes to Floci's log, prefixed emr-serverless:<jobRunId>. With an S3 log destination, the run's s3MonitoringConfiguration or else the application's, its standard output and error also go to Floci's S3 once the run ends, gzipped, as stdout.gz and stderr.gz under <logUri>/applications/<applicationId>/jobs/<jobRunId>/SPARK_DRIVER/, with attempts/<n>/ before SPARK_DRIVER/ for a STREAMING run, or a BATCH run whose retryPolicy allows more than one attempt, on release 7.1.0 or later, each attempt's logs under its own number. A cancelled run's logs hold what its driver wrote until it was stopped. Logs that cannot be written, to a bucket that does not exist say, leave the run as it ended. * CloudWatch Logs: with CloudWatch logging enabled, the run's cloudWatchLoggingConfiguration or else the application's ("enabled": false at the run turns it off), the driver's standard output and error go line by line, while it runs, to the log streams <prefix>/applications/<applicationId>/jobs/<jobRunId>/SPARK_DRIVER/stdout and .../stderr in Floci's CloudWatch Logs, with attempts/<n>/ before SPARK_DRIVER as for S3. The log group is logGroupName, /aws/emr-serverless by default, and <prefix> the logStreamNamePrefix, if any; both are created as needed, in the run's account and Region. A logTypes sends only the driver's types it names, and none of the driver's output when it names only SPARK_EXECUTOR. * Image: an application's custom image runs in place of the release's: the Driver worker type's imageConfiguration in workerTypeSpecifications for the driver and the Executor worker type's for the executors in containers of their own (local mode runs them in the driver's container), or else the application's imageConfiguration, which applies to every worker type. An <account>.dkr.ecr.<region>.amazonaws.com/<repository>:<tag> URI leads to Floci's ECR, as a Lambda function's or an ECS task's image does, so the image is pushed to a repository there; the repositoryUri Floci's ECR hands out works too. The image is pulled again for every run, so a tag pushed again is what the next run gets; when the pull fails the image the Docker daemon already has runs, one built locally under that URI included, and without one the run is FAILED with "Job run could not start". CreateApplication refuses an image configuration without an imageUri, and CreateApplication and UpdateApplication an image whose ECR repository, AWS-shaped or a repositoryUri from Floci's ECR, is in another Region, both with ValidationException in Floci's own wording. An update that leaves imageUri out removes that image configuration. Without a custom image, image-template names another image than the release's, such as a mirror or a dated tag of it: registry.internal/emr-serverless/spark/%s:20250425. GetJobRun reports the image configurations each attempt applies, as its application had them when the attempt was made: its imageConfiguration, and its worker types' in workerTypeSpecifications (those the application resolved as it started, with that digest), as AWS's do when digests are resolved for each run ("To identify which image version each job is running, the GetJobRun API response returns the resolvedImageDigest for that specific job"). The driver's configuration, its worker type's or else the application's, has the resolvedImageDigest of the image the attempt pulled for the driver, its manifest digest in Floci's ECR; the executors' has theirs, or the driver's where the two share one. No other has a digest, even one naming the same image, such as the Executor image while local mode runs the executors in the driver's container, or a Hive run's TezTask image. Nor does one built locally under that URI, nor any without the docker runner mode, which pulls no image. * Architecture: a run's containers, its driver's and its executors', run on the Docker host's own platform by default. With honour-architectures on (FLOCI_SERVICES_EMRSERVERLESS_HONOUR_ARCHITECTURES=true) they run the image for its application's architecture, linux/amd64 for X86_64 and linux/arm64 for ARM64, the release's images being published for both and a custom image pulled for that platform; an application that names none still runs on the host's own, where on EMR Serverless "x86_64 is the default option". It is off by default, as Lambda's is, because tools such as Terraform name X86_64 unless told otherwise, which on an arm64 host would move every run to emulation. A host of another architecture runs the image under emulation, which Docker Desktop has and a Linux host gets from QEMU's binfmt_misc handlers; without it the driver cannot start ("exec format error") and the run fails. Floci does not fall back to the host's platform when the setting is on. CreateApplication and UpdateApplication refuse an architecture other than ARM64 or X86_64, the model's enum, with the framework's ValidationException.

    Running Hive job runs

    With runner-mode set to docker, a Hive application's job run executes too. Floci starts one container per run from the application's custom image, if it names one, or else from the release's Hive image, the base image AWS publishes for customizing EMR Serverless Hive images (public.ecr.aws/emr-serverless/hive/<release>), and runs hive in it, with Tez in local mode, in Hive's JVM: the container holds the Hive driver and its Tez tasks. The custom image is the HiveDriver worker type's imageConfiguration in workerTypeSpecifications, or else the application's imageConfiguration; a TezTask image is not used, as Tez's tasks run in the driver's container.

    • States, credentials, HTTPS and the image: as for a Spark run, above, the driver being hive. The first run of a release pulls its Hive image, 2.7 GB unpacked. Without a custom image, hive-image-template names another image than the release's: registry.internal/emr-serverless/hive/%s:20250425.
    • What hive gets: the properties of the core-site, tez-site and hive-site classifications, each a --hiveconf, from the application's runtimeConfiguration or the run's own configurationOverrides.applicationConfiguration, which replaces the application's whole classification; then the run's initQueryFile and query, which Hive reads from Floci's S3 and runs in that order; then its parameters, split as a shell would split them, so a --hiveconf there takes priority over the classifications, as the user guide ranks them. Before them all come Floci's own settings, which any of them replaces: S3A on Floci's S3 for s3://, the Glue Data Catalog client, the image's metastore, on Floci's Glue with the run's account as its hive.metastore.glue.catalogid (a hive-site one names another account's catalog), and Tez in local mode. emrfs-site is not applied, as s3:// goes through S3A rather than EMRFS.
    • Scratch and warehouse folders: hive.exec.scratchdir and hive.metastore.warehouse.dir, which the user guide makes mandatory, are used as the run sets them, in Floci's S3. Hive runs as the image's hadoop user, in its home folder; Tez in local mode copies its session's staging folder, which Hive puts under the scratch folder, to the same path in the container, so Floci makes that path hadoop's before Hive starts.
    • Output: the driver's standard output, where Hive prints a query's results, and its standard error, where the Hive CLI prints its progress and errors, go to Floci's log, prefixed emr-serverless:<jobRunId>. With an S3 log destination they also go to stdout.gz and stderr.gz under <logUri>/applications/<applicationId>/jobs/<jobRunId>/HIVE_DRIVER/ once the run ends, and with CloudWatch logging to the log streams .../HIVE_DRIVER/stdout and .../HIVE_DRIVER/stderr while it runs, as a Spark run's go under SPARK_DRIVER; a logTypes takes the driver's types from its HIVE_DRIVER entry.

    Limitations and Differences from AWS

    • Jobs do not execute by default: in the immediate runner mode StartJobRun records a job run and moves it through its states, but nothing runs. In the docker mode a Spark run executes in Spark's local mode in one container unless executor-containers is above 0 (see Executors below), and a Hive run with Tez in local mode in one container: in local mode, worker counts and sizes, initial and maximum capacity are not applied. A driver's failure is FAILED in Floci's own wording. Of the monitoring configuration, the S3 log destination gets the driver's stdout.gz and stderr.gz once a run ends (no event logs, rotated files or uploads while it runs), and CloudWatch Logs the driver's output while it runs (no executor logs, which local mode does not have and executors' containers take with them, no HIVE_LOG, TEZ_AM or TEZ_TASK logs of a Hive run, whose own log stays in its container, and encryptionKeyArn is ignored).
    • Executors: with executor-containers above 0, a Spark run's executors run in containers of their own, but at most executor-containers of them, rather than as many as dynamic allocation asks for, and a container's memory and cores are not limited to its worker's size, which only Spark's settings follow. initialCapacity is not applied: no worker is waiting, so each starts as the run asks for it. Spark's master is Spark's own standalone master, in the driver's container, where EMR Serverless has its own (spark.master reads spark://...), and the driver's UI, which the release's image turns off, is on, with its kill links off, as Floci follows the driver through it: a run that turns it off again (spark.ui.enabled=false) gets a single executor container 30 seconds after its driver starts, whose worker offers 32 cores and 256 GB, as Floci cannot read the run's own sizes, and which, like its driver's, counts for nothing against the application's maximumCapacity.
    • A driver that is not its application's type: AWS documents no answer for a hive run on a Spark application, or a sparkSubmit run on a Hive application. In the docker mode Floci records such a run, then fails it without running, in Floci's own wording, as its application's image could not run it.
    • Mandatory Hive properties: Floci does not refuse a Hive run without hive.exec.scratchdir or hive.metastore.warehouse.dir. Hive then keeps its scratch files and its managed tables' data in the container, which go with it.
    • Unsourced errors: AWS documents neither the error for a run submitted to an application whose auto-start is off nor the one for a run on a terminated application; Floci answers both with ValidationException. The same holds for a BATCH timeout outside 1 to 10080 minutes on emr-7.11.0 or later (ValidationException) and for GetJobRun naming an attempt a run never made (ResourceNotFoundException), both in Floci's own wording. A run needs a jobDriver, as every JobRun carries one, and jobDriver is a union, so a run without a driver, or with one that sets both sparkSubmit and hive or neither, is refused with ValidationException too, in Floci's own wording.
    • Archives: only the archives of spark.archives that are in S3 are unpacked into the driver's working directory; Spark alone unpacks the others, into its own files folder. Floci reads an archive itself, whatever the execution role may read, though Spark's own read of it uses the role's credentials.
    • Custom images: Floci does not check an imageUri against the model's pattern, which would refuse the repository URIs Floci's own ECR hands out, nor that the image was built from its release's base image (AWS refuses one that was not from emr-7.14.0 and emr-spark-8.1.0 on), nor the image's size. An image that cannot be pulled fails the run, not the request that names it. An image's digest is resolved as the application starts where its applicationLevelDigestResolution is true, or left unset on EMR 7.13 or earlier, as the user guide's table has it, and AWS's "Custom images are resolved to a digest at application start; that digest is used for all jobs until the application restarts": the application's image configuration gets the digest of the image in Floci's ECR as its resolvedImageDigest, and each run pulls the image by it until the application starts again; a stopped application reports none. An image outside ECR, one in another account's repository (Floci does not check that the application may pull it), or one Floci's ECR does not hold or cannot read without Docker, has no digest to read and is resolved for each run, as every image is from 7.14 on; any other answer from Floci's ECR fails StartApplication with InternalServerException; such a run's digest comes from its attempt's own pull (see Image above), and a job run's image configurations carry no applicationLevelDigestResolution.
    • Not emulated: the "EMR Serverless Job Run Retry" event, as Floci sends no EMR Serverless events, the account's limit of 2000 QUEUED runs, a session's totalResourceUtilization and billedResourceUtilization, and a Hive run's (see Resource utilization), and Flex capacity (flexExecution is kept and given back only).
    • Instant Start/Stop: Floci marks the application STARTED or STOPPED immediately without provisioning actual compute capacity in the background.
    • Sessions in the immediate mode run nothing: a session is kept with its lifecycle, but no Spark driver runs for it, and a Spark Connect call to it is refused; the docker mode runs one (see Running a session's Spark Connect server).
